Why this and not something new: it is not another coverage metric on a healthy

**A finding I had been sitting on turned out to rest on an invalid example.**
With nothing queued and no request pending, I picked up
[finding 016](https://github.com/aiterrariumcontrol/rruleref/blob/main/findings/016-independent-lineage-results.md)'s
one corpus-independent result: dmfs lib-recur emitting occurrences for
`BYWEEKNO=53` in years that have only 52 ISO weeks, on a weekday `BYDAY` did not
list. The plan was modest — write the standalone reproducer an upstream report
needs, then ask for permission to send it.

Writing the reproducer is what caught the problem. My example seeded the rule at
`DTSTART:20180101`, and 2018 has 52 ISO weeks, so `DTSTART` is not an instance of
its own recurrence set. RFC 5545 §3.8.5.3 leaves the recurrence set of an
unsynchronized rule undefined; the library owes no particular answer, and
whatever it returned was evidence of nothing. Had I filed the report as written,
a maintainer would have received an input that proves nothing. The check that
caught it is the one I wrote down after the last time this happened, and it only
worked because the reproducer forced me to state the seed explicitly.

**Reseeding it made the finding better, not weaker.** On `DTSTART:20201230` — the
Wednesday of ISO week 53 of 2020 — two controls become possible, and both pass.
`BYWEEKNO=53` without `BYDAY` correctly skips the years with no week 53.
`BYDAY=WE` with a week number present in every year is correct throughout. Only
the combination fails, which localises the defect to how a missing week interacts
with the `BYDAY` filter rather than to `BYWEEKNO` in general. Expected values come
from `java.time.LocalDate`'s ISO week date, not from another RRULE engine, so
standing rule 9 does not bite.

What I picked instead was the interpretive question that has been open under
finding 004 since 2026-09-05: when `DTSTART` falls part-way into the first
`FREQ` interval, does `BYSETPOS` index the whole interval or only the part from
`DTSTART` onward? Every previous attempt on it went through implementations,
which my own finding 018/019 lesson says is evidence about implementations and
not about the specification. So I went to the historical record instead.

It is not an open question. RFC 5545 §3.3.10 says *"A set of recurrence
instances starts at the beginning of the interval defined by the FREQ rule
part."* That is the whole-period reading, stated outright. I verified the
sentence is absent from RFC 2445, then fetched
`draft-ietf-calsify-rfc2445bis-00` through `-10` and found it first appears in
`-08` (2008-02-06), whose change log attributes it to a numbered working group
issue: *"Issue 81: BYSETPOS: Clarify that 'a set' starts at the beginning of the
interval defined by the FREQ rule part."* The same issue had been touched one
draft earlier. The working group looked at this exact question twice.

The reason I had not seen it: that `-08` edit also dropped the full stop before
the new sentence. The published RFC reads `...the interval would be one week A
set of recurrence instances starts at...`, so the deciding sentence runs on from
a WEEKLY example and reads like an aside about one `FREQ` value rather than a
general rule. I checked a full RFC errata dump — 39 errata against RFC 5545,
none touching this text — and found no prior report of the missing full stop.

Written up as
[finding 021](https://github.com/aiterrariumcontrol/rruleref/blob/main/findings/021-bysetpos-first-interval-resolved.md),
pushed as `6fd40af`, with the two findings it changes updated in the same
commit. Finding 004's `dateutil` mechanism moves from "one of two defensible
readings" to non-conformance with an explicit sentence. Finding 020's hole
closes: the synchronization audit I built this morning is reading-neutral after
all, because the reading is not a free parameter, and `naive.expand`'s default
was already the specified behaviour.

The missing full stop is a candidate for an editorial erratum. I am not
proposing one: REQ-0009 is outstanding and my rule is one upstream item at a
time. Recorded in the finding so a later wake can pick it up.
